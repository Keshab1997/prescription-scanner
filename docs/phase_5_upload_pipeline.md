# Phase 5 — Camera, Crop, Validation & Private Upload

## Implemented

- Camera capture through `image_picker`
- Gallery selection using the platform picker
- Android interrupted-pick recovery
- Native crop and rotate experience
- JPEG normalization with EXIF removal
- Client compression targeting a practical upload size
- Minimum resolution validation
- 10 MB client limit
- SHA-256 content hash
- Secure upload reservation through `create_prescription_upload`
- Upload to the private `prescriptions` Storage bucket
- UUID ownership path generated by the database
- `upsert: false` to avoid replacing an existing object
- Friendly quota, maintenance, blocked-user and upload errors
- Local temporary copy cleanup
- Best-effort reservation rollback when Storage upload fails

## Apply the small Phase 5 migration

Open Supabase SQL Editor and run:

```text
supabase/migrations/202608130002_upload_cleanup_rpc.sql
```

This creates only `cancel_prescription_upload(uuid)`. It lets an authenticated owner cancel their own `uploaded` reservation if the Storage request fails. It cannot delete another user's prescription or a job that already started processing.

## Android configuration

The bootstrap script now adds:

- `android.permission.CAMERA`
- Supabase authentication deep-link intent filter
- `UCropActivity` required by the image cropper

Gallery selection does not add broad media-library permission.

## Current flow

```text
Camera / Gallery
  → Native crop or rotate
  → Remove EXIF and compress
  → Validate dimensions and size
  → SHA-256 hash
  → Reserve prescription row through RPC
  → Upload private object
  → Open Processing screen with prescription ID
```

## Important current limitation

The Processing screen does not invoke Gemini yet. That is Phase 6. Until a valid Gemini provider is configured and `ai_enabled` is set to true, the upload-reservation RPC intentionally returns `AI_DISABLED`.

## Acceptance test after Phase 6 configuration

1. Sign in as User A.
2. Pick a clear prescription from gallery.
3. Crop and rotate it.
4. Confirm the optimized size and dimensions are shown.
5. Upload it.
6. Confirm a row exists in `prescriptions` with User A's UUID.
7. Confirm the object path is `{user_uuid}/{prescription_uuid}/original.jpg`.
8. Confirm the Storage bucket is private.
9. Attempt to read the path as User B and confirm access is denied.
10. Select a low-resolution image and confirm it is rejected before upload.
11. Simulate a Storage failure and confirm the reservation is cancelled.
